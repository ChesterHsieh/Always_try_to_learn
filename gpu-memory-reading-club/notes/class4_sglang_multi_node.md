## 1. 開場框架：用「經典分散式系統的問題清單」當影子

**這一堂不要一開場就講 EP 或 router。** 先問聽眾一個更大的問題：

> **任何分散式系統，理論上都會遇到哪些共同問題？**

讓他們自己列，通常會列出下面這八類（教科書分類）。然後**一格一格對照到 GPU 推論叢集**——重點不是把不適用的劃掉，而是看清楚**底層結構的共同性**：哪些是被**規避**掉的（不是被解決）、哪些**變形**了、哪些反而被**放大**成核心工程難題。

### 1.1 八類經典問題 × GPU 推論叢集

| # | 經典分散式系統問題 | 在 GPU 推論叢集裡 | 判定 |
|---|---|---|---|
| 1 | **時間與順序**：沒有全局時鐘、Lamport / Vector clock | 不需要邏輯時鐘——通訊模式是 SPMD 事先規劃好的，不是執行期協商出來的。但**變形**成 barrier 同步與 pipeline bubble：各卡速度不一致造成的等待浪費 | **變形**（因果順序 → 同步開銷） |
| 2 | **一致性**：多副本、CAP、強／最終一致性 | 沒有「多副本各自更新再收斂」的場景。**但一個影子確實存在**：router 對「每台機器的 radix tree 裡有什麼」只有**近似且過時的視圖** | **大部分規避，但「快取視圖不一致」是真問題** |
| 3 | **容錯**：部分失效、拜占庭、故障偵測 | 拜占庭**不用考慮**（自己控制的受信任封閉環境，只有 fail-stop）。但**部分失效完全存在且被放大**：一張卡掉，整個 TP group 廢掉。故障偵測仍難——「掛了」與「慢了」分不清（straggler） | **簡化為 fail-stop，但部分失效是核心** |
| 4 | **共識**：Paxos / Raft、FLP 不可能定理 | 計算路徑上**不需要**。集合通訊（AllReduce / All-to-All）是確定性的、框架事先規劃好的，不是「誰的意見對」的協商。（Raft 可能出現在外圍控制平面，如 job scheduler、metadata store） | **規避** |
| 5 | **通訊**：丟失、延遲、重複、亂序、網路分區 | 訊息可靠性由 RDMA / NCCL 底層保證，不用自己處理。但**問題換了一根軸**：從「會不會丟」變成「**頻寬夠不夠、延遲多少、拓撲怎麼走**」——這是整個第二堂的內容 | **換軸：可靠性 → 效率** |
| 6 | **並發與競態**：分散式鎖、2PC / 3PC | 沒有多節點對同一份可變資料的衝突寫入 → 不需要鎖或事務協議。**邊緣有影子**：PD 分離時 KV cache 的所有權從 prefill 機轉移到 decode 機，中間誰負責釋放？ | **大部分規避，邊緣有影子** |
| 7 | **可擴展性**：協調開銷非線性、負載均衡、分片 | **完全存在且被放大成核心痛點**：all-to-all 通訊量隨 EP 規模成長、快取局部性 vs 負載均衡、**專家負載不均＝經典的資料傾斜（data skew）** | **放大** |
| 8 | **可觀測性**：沒有單一全局視角 | **完全存在**：掉卡偵測、慢節點偵測、每台的快取命中率與 KV 池佔用。router 要做好決策就需要全局視角，但它只有近似的 | **存在** |

### 1.2 共同的底層結構（這一頁是本堂的立論）

所有分散式系統的問題，往下挖都來自**三個物理事實**：

1. **沒有共享記憶體** → 資訊必須靠傳遞，傳遞需要時間 → **任何「全局視角」都是過時的**
2. **部分失效** → 系統的一部分可以壞掉，而其他部分不知道，也分不清「壞了」還是「慢了」
3. **協調需要通訊** → 協調越多，通訊越多，擴展性越差

GPU 叢集之所以能「規避」很多經典問題，**不是因為它更聰明，而是因為它主動放棄了兩樣東西換取簡化**：

| 放棄了什麼 | 換到什麼 |
|---|---|
| 放棄「互不信任」→ 封閉、受信任、同構的環境 | **拜占庭容錯不用做** |
| 放棄「執行期協商」→ 通訊模式由 SPMD 程式事先規劃 | **共識協定不用做** |
| （訓練）放棄「持續可用」→ fail-stop + checkpoint 重啟 | **CAP 取捨不存在** |

**代價是：它把全部的複雜度壓到「效率」這一根軸上。**

> **一句話對比**：
> 經典分散式系統在問「**怎麼保證正確**」；GPU 叢集在問「**怎麼不浪費**」。
> 前者的敵人是不確定性，後者的敵人是閒置與等待。**但兩者面對的物理事實是同一組。**

### 1.3 關鍵轉折：推論服務比訓練更「像」傳統分散式系統

這是本堂最值得講的一個觀察，也是它和第二堂的分水嶺：

| | 訓練（第二堂） | 推論服務（本堂） |
|---|---|---|
| 性質 | 一個 batch job | **長期在線服務，有 SLO** |
| 掛一台怎麼辦 | 整個 job 停下、從 checkpoint 重啟即可 | **不能停整個服務** → 可用性重新變成真問題 |
| 有沒有狀態散在各機 | 參數每步同步，沒有分歧 | **有**：KV cache 散在各副本，router 的視圖是近似的 |
| 負載 | 事先決定、均勻 | **執行期才知道**、長度差異巨大、有熱點 |

**所以第三個放棄（放棄持續可用）在推論這邊收不回來。** CAP 那一軸、故障偵測、快取視圖不一致——這些在訓練場景可以忽略的東西，在推論服務裡**部分回來了**。這正好解釋了為什麼第二堂不需要 router 與容錯策略，而本堂需要。

### 1.4 三個「換個名字的老問題」（收尾用）

講到後面可以回頭指出，本堂的問題其實都有分散式系統的老對應：

| 本堂的問題 | 它其實是 | 老領域裡的同一個問題 |
|---|---|---|
| 專家負載不均（問題⑤） | **資料傾斜（data skew）** | 分散式資料庫的分片熱點 |
| 快取局部性 vs 負載均衡（問題⑦） | **locality vs balance 的取捨** | CDN 邊緣快取放置、一致性雜湊、分散式快取 |
| KV 該搬還是該重算（問題⑦） | **快取失效成本 vs 重建成本** | 任何多層快取系統的核心決策 |

> **講法**：這裡可以說一句——「**你們如果做過分散式資料庫或 CDN，這一堂大部分內容你們已經會了，只是名詞換了。**」這對有後端背景的聽眾特別有共鳴。

## 3. 問題⑤ 大 MoE 放不下 → 大規模專家平行

- **前提澄清**：MoE 的「每 token 只活躍一小部分專家」在**單卡上不省容量**（所有專家都要在 HBM），只省每 token 的 FLOPs 與權重讀取。要連容量也省，必須 **EP：把 256 個專家散到幾十上百張卡，每張卡只放幾個**。
- **收益**：每卡權重變小 → 每卡讀的位元組數變少 → decode 步時下降（回到第三堂的 AI ≈ B 那把尺）
- **代價**：每層兩次 **all-to-all**（token 送去對應專家、算完送回）→ 通訊變主角（第二堂的頻寬階梯）
- **新問題：專家負載不均**（＝資料傾斜）：熱門專家所在的卡塞爆，其他卡閒著
  - 推論期：**EPLB**（Expert Parallelism Load Balancer）做專家副本與重排
  - 訓練期：DeepSeek 的**無輔助損失偏置調整**維持均衡
- **配套 kernel**：DeepEP（all-to-all 通訊庫）、DeepGEMM（FP8 GEMM）、FlashMLA（MLA decode kernel）——DeepSeek 開源，SGLang 整合

### 落地數字（用來說服人）

| 系統 | 硬體 | 數字 |
|---|---|---|
| DeepSeek 官方 V3/R1 推論系統 | H800 節點（8 卡） | 73.7k input / 14.8k output tok/s 每節點；prefill EP32、decode EP144 |

## 4. 問題⑥ P/D 互擾 → PD 分離

- **動機**：prefill 是 compute-bound、decode 是 memory-bound，**最佳配置根本不同**
  - Prefill 群：大 TP、小批、追 FLOPs 利用率與 TTFT
  - Decode 群：大 EP、大批、追頻寬與 KV 容量
- **中間傳的是 KV cache**：走 NVLink / RDMA。vLLM 用 KV connector 抽象（生產環境接 LMCache + NVIDIA NIXL）、SGLang 有自己的 PD 分離、NVIDIA Dynamo 也是這條路線
- **代價**：多一次 KV 傳輸、多一層調度複雜度
- **好處**：兩邊各自開到最佳點，且**可以分開擴縮容**（這點很重要——prefill 與 decode 的負載比例會隨流量型態變動）
- **第三堂的 chunked prefill 只是緩解**，PD 分離才是根治
- **經典問題的影子**：KV 的**所有權轉移**——prefill 機算完交給 decode 機，中途誰負責釋放？decode 機還沒接手就掛了怎麼辦？這是 6（並發／事務）在這個領域的最小形式

## 5. 問題⑦ 多副本怎麼分流 → cache-aware router（本堂核心）

### 5.1 矛盾的產生

**前提**：多台機器各自維護獨立的 radix tree，**彼此的 KV cache 不共享**。

- **Round Robin（輪詢）**：完全不看內容 → 本該共享前綴、集中在同一台處理的請求被打散 → **命中率崩潰**
- **內容感知路由**（同一份文件的請求固定送同一台）→ 該機器負載暴漲（**hot spot**），其他機器閒置

**核心矛盾：快取局部性 ⟷ 負載均衡，此消彼長。** 這正是 §1.4 說的老問題——跟 CDN 邊緣快取、分散式資料庫分片熱點是同一個結構。

### 5.2 解法方向：cache-aware load balancing

- Router 同時看兩件事：**前綴命中程度**（把請求送去「已經有這段前綴」的機器）與**該機負載**（佇列積壓、KV 池佔用）
- 當某台負載超過閾值、且它上面有「高價值」（被大量複用）的快取時，**主動把該快取複製（replicate）到空閒機器**，讓新請求可以分流
- Router 自己維護一份**近似的** radix tree 視圖（它不可能即時知道每台的確切快取狀態）→ 這就是 §1.1 第 2 類（一致性）在這裡的真實形態

### 5.3 該搬還是該重算（建議當本堂的壓軸推導）

複製 KV 不是免費的。要算一筆帳：

```
搬的成本 = KV 大小 ÷ 互連頻寬
重算的成本 = 該段前綴的 prefill 時間
```

用第三堂的數字（Llama-3-8B，128 KB/token）與第二堂的頻寬階梯：

| 前綴長度 | KV 大小 | 走 NVLink（~900 GB/s） | 走 IB（~50 GB/s） | 重新 prefill |
|---|---|---|---|---|
| 2,000 token | 256 MB | ~0.3 ms | ~5 ms | 數十 ms |
| 32,000 token | 4 GB | ~4.5 ms | ~80 ms | 數百 ms ~ 秒級 |

> **這個比值決定一切**：NVLink 域內幾乎永遠該搬；跨節點走乙太就要算清楚；前綴越長越該搬（重算是 O(n²)、搬是 O(n)）。
> **這一頁把第二堂（頻寬階梯）、第三堂（KV 每 token 多少 bytes）、第四堂（路由決策）三堂串成一條線**，很適合當壓軸。

### 5.4 業界對應

Cache-Aware Load Balancing / KV Cache Replication —— SGLang Router、**Mooncake**（Moonshot／Kimi 的 KVCache-centric 分離式架構）、vLLM 的 KV 傳輸（LMCache / NIXL）、NVIDIA Dynamo 的 KV-aware routing。

> 💡 **可以回扣第五堂**：Mooncake 是 Kimi 的**服務層**，而[第五堂](class5_china_models.md)講的 Kimi K2/K3 是**模型層**——同一家公司在兩個高度上各解一半問題。

## 6. 問題⑧ 容錯（待補，但框架已經有了）

### 6.1 鑰匙：KV cache 是「可重算的快取」，不是「不可回復的狀態」

- KV cache 完全由 prompt token 決定 → **掉了可以重算，只是慢，不會錯**
- 所以副本掛掉時的預設策略是「請求重送到另一台、重新 prefill」，而不是「想辦法把 KV 救回來」
- 推論：**KV 複製／傳輸的動機不是可靠性，而是省算力**（避免重算）

> 這一點想通了，問題⑦（負載均衡）和問題⑧（容錯）的關係就清楚了：**它們用的是同一套機制，但動機完全不同。**

### 6.2 待查證的細節

| # | 問題 | 方向 |
|---|---|---|
| 1 | 進行中的請求怎麼重試？使用者會看到什麼？ | 串流已吐出一半的 token 怎麼辦——重頭來過還是接續？各家實作 |
| 2 | PD 分離下 prefill 完成、decode 機掛掉 | KV 已經傳過去了，算力已經花了 → 這是最貴的失敗模式 |
| 3 | 故障偵測：掛了 vs 慢了 | straggler 與 dead node 的區分；健康檢查與逾時設定 |
| 4 | 一張卡掉，整個 TP group 廢掉 | TP 內部沒有容錯——這是「部分失效被放大」的具體形態 |
| 5 | 橫向比較：SGLang / vLLM / Mooncake / DeepSeek | 做成「問題 × 廠商」矩陣當收尾 |

## 8. 幾個會被問到的澄清（沿用第三堂的判準）

- **「請求怎麼分配」和「模型怎麼切」是兩個層級**：一個副本可能自己就橫跨 8 張卡（TP=8），router 眼中它仍是「一台」。模型並行是第二堂 Part B 的內容，本堂只需一頁帶過。
- **可以快取的是「計算結果」，不可以快取的是「請求狀態」**（第三堂問題②×③ 的紅線）：KV 是計算結果所以可跨機複製；FSM 狀態、取樣種子屬於請求，不能。
- **「RadixAttention vs PagedAttention」是假對立**（第三堂第 11 頁）：一個是記憶體配置層、一個是索引複用層。
