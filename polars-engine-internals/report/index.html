Polars 2.0 引擎轉向

2.0 的核心改動在 Rust 裡只是一個 match 分支：Engine::Auto 從 InMemory 改成 Streaming。為了讓這一行能安全地翻過去，團隊花了兩年多重寫一顆 streaming 引擎、刪掉舊的那顆、放寬行順序的語意，最後在發布前一天打開了 spill-to-disk。這份報告把技術選型、卡關點和決策因素攤開，每一段都指回原始碼。

8.3k → 21.4koptimizer 目錄行數

  1. 記憶體下降主要來自執行模型的改變，spill 不是主因。1.x 的 in-memory 引擎每個運算子都回傳一整個 DataFrame；2.0 的 streaming 引擎讓約 10 萬列的 morsel 在容量為 1 的通道裡流動，來源端還有預取位元組上限、row group 統計跳過與延遲解碼。
  2. 以前不做，是因為舊的 streaming 引擎（polars-pipe）撐不起「預設」。它靠白名單決定能不能串流，鎖步執行，順序靠一個全域計數器，最常見的 group-by 和所有 join 都不能 spill。團隊選擇重寫，而不是擴充。
  3. 新引擎是 morsel-driven、push-based、async 的設計。每個節點以 async 任務執行，MorselSeq 加 linearizer 在平行之下還原順序，consume token 與 SourceToken.stop() 提供背壓，pipeline breaker 把執行切成多個 phase。
  4. 真正需要 major 版號的是行順序。join、group_by、unpivot 不再保證「順便」的順序，optimizer 的 simplify_ordering 會把沒人觀察的順序約束拿掉，讓引擎能亂序平行。
  5. 2.0 的 optimizer 也開始往 cost-based 走：基數估計、貪婪 left-deep join reordering、join runtime filter。這些都在 2.0 前六週才合併，仍屬早期。

01一行 match 的翻轉

先把「2.0 到底改了什麼」講精確。Python 端 collect(engine="auto") 的預設值在 1.x 和 2.0 都一樣，差別在 Rust 端把 Auto 解析成哪一顆引擎：

// py-1.44.2（最後一個 1.x）crates/polars-lazy/src/frame/mod.rs
Engine::Auto => Engine::InMemory,

// py-2.0.0 同一個函式 collect_with_engine
Engine::Auto => {
    if self.opt_state.eager() { Engine::InMemory } else { Engine::Streaming }
},

來源：py-1.44.2 frame/mod.rs#L637-L642 · py-2.0.0 frame/mod.rs#L634-L646 · PR #27822（2026-06-27 寫成，2026-08-26 合併，首次出現在 py-2.0.0-rc.1）

Eager 的 DataFrame 操作仍走 in-memory（_eager_engine()）。想退回舊行為，可以用 pl.Config.set_engine_affinity("in-memory") 或環境變數 POLARS_ENGINE_AFFINITY=in-memory（_select_engine、enum Engine）。sink_* 本來就一律走 streaming，所以不受影響。

升級指南把這條列為第一個 breaking change，並放了一個 danger 框：streaming 引擎對不需要順序的運算（unpivot、group_by、join…）不保證行順序（upgrade/2.md#L5-L23）。官方的 2.0 預發布文章也直接說，之所以要升 major 版，就是因為這個順序語意的改變。

02記憶體為什麼小那麼多

先看數字。下面三組都不是我實測的：第一組是第三方作者的單次測試，後兩組是 Polars 官方在 2025 年 5 月用 1.30.0 跑的 PDS-H（衍生自 TPC-H，非稽核結果），屬於廠商自測。

機制可以從同一個查詢在兩顆引擎裡的形狀看出來：

把上圖拆成四個機制：

① 中間結果不物化，通道容量是 1

節點之間的 port 是 single-producer、single-consumer、容量 1 的 connector（connector.rs#L15-L24）。distributor 與 linearizer 的緩衝預設各 4 格（polars-stream/lib.rs#L36-L52），morsel 大小預設 100,000 列（POLARS_IDEAL_MORSEL_SIZE，polars-config/lib.rs#L36-L37）。上游塞滿了就只能等，所以在途資料大約是「pipeline 數 × 少數幾格 × 10 萬列」這個量級。

② 來源端的預取有預算

Parquet 讀取用兩個 semaphore 組成 PipelineBudget，一個限數量、一個限 KB：數量是 max(2 × pipelines, inflight)，夾在 16 到 2048 之間；KB 是 4 × pipelines × chunk_size。原始碼註解寫著「大資料集多半是 KB 上限先生效」（parquet/builder.rs#L80-L115、pipeline_budget.rs#L11-L35）。CSV 也有 POLARS_CSV_CHUNK_PREFETCH_LIMIT（預設 2 × pipelines）。

③ 不需要的資料根本不解碼

Predicate 會被改寫成對 min/max/null_count 的測試（例如 col > 5 變成檢查 col_max，skip_batches.rs#L152-L167），整個 row group 在抓取前就跳過（row_group_data_fetch.rs#L162-L168）。留下來的 row group 走 prefilter，也就是延遲物化：先解 predicate 欄位，再用 Filter::Mask 只解碼保留列的其他欄位（row_group_decode.rs#L623-L700，自 #22190 起預設啟用）。對照 1.0 的 in-memory parquet scan：它把每個檔案讀成 Vec<DataFrame> 再垂直合併，有 row index 時甚至整份讀完才套 predicate，註解自己寫了「This is inefficient」（1.0 scan/parquet.rs#L318-L358）。

④ pipeline breaker 只留狀態，一次只跑一個吃記憶體的

Group-by 邊吃邊聚合，hot table 命中的 key 就地累加。排程器每個 phase 最多只跑一個「memory-intensive pipeline blocker」，除非剩下的全是 sink（find_runnable_subgraph，execute.rs#L62-L150）。宣告自己吃記憶體的節點包括 GroupBy、Sort、各種 Join、Window、InMemorySink。

推論 那個 4.76 GB → 691 MB 的落差應該和 spill 無關。OOC 的預設門檻是可用 RAM 的 80%（polars-config/lib.rs#L75-L85），4.76 GB 在一般機器上碰不到，而且 OOC 直到 2.0.0 才預設開啟（#29741，2026-10-05，比 rc.1 還晚）。落差主要來自上面的 ①～④。spill 解決的是另一個問題：pipeline breaker 的狀態真的大過 RAM 的時候（見 6.3）。

03新引擎怎麼跑

從 CMU 15-445/721 的角度看，Polars 裡同時存在兩種執行模型。in-memory 引擎是 operator-at-a-time、整批物化，比較接近 MonetDB 的 BAT 模型，和 Volcano 那種一次 next() 拿一個 tuple 的 iterator 不同。2.0 預設的 streaming 引擎則是 morsel-driven、push-based，相當接近 Leis 等人 2014 年的 Morsel-Driven Parallelism：固定大小的資料塊、每個 worker 一條 pipeline、pipeline breaker 把執行切成多個階段。morsel 內部的運算維持向量化、columnar，沒有 JIT。

原始碼裡沒有任何註解直接引用 HyPer 或 Leis。Polars 2025 年 12 月的 "Polars in Aggregate" 文章則把 Morsel-Driven Parallelism 列為設計參考。

一個 query 從 Python 進來後，會經過這些層：

每個節點有兩個責任。update_state 協商每個 port 的 PortState::{Blocked, Ready, Done}（graph.rs#L211-L216），spawn 在每個 phase 開出 async 任務。port 兩端各自宣告要 serial 還是 parallel，框架依組合自動插入 distributor（serial→parallel）或 linearizer（parallel→serial）（pipe.rs#L84-L109）。

execute.rs#L298-L414 · 狀態收斂 graph.rs#L98-L180

這一段是整個設計最關鍵的部分。update_all_states 用 worklist 反覆呼叫各節點的 update_state，直到沒有任何 port 狀態再改變；從 Done 轉出去會直接報錯。接著 find_runnable_subgraph 找出 pipeline blocker（輸出全被擋住、但有輸入就緒的節點），再沿著兩端都 Ready 的 pipe 往回擴張。每個 pipe 的 seq_offset 跨 phase 保留，所以順序在 phase 之間也成立（#L159-L171）。

執行器是 Polars 自己寫的（2.0 時搬進獨立 crate polars-async，#27629）。它有兩個優先級：source 用 Low，pipe 與運算用 High，讓「消化」優先於「生產」（executor/mod.rs#L59-L64）。每條執行緒有一個 LIFO local slot 加一個可被偷的佇列，偷工作時先找同一個 NUMA 區域（#L256-L310，NUMA 感知來自 #28464）。

04為什麼 1.x 不這樣做

1.0 其實已經有一顆 streaming 引擎：crates/polars-pipe，透過 collect(streaming=True) 開啟，文件標為 unstable。它沒辦法變成預設，原因在設計本身：

逐項看舊引擎的天花板：

面向1.0 的 polars-pipe2.0 的 polars-stream
能不能串流在計畫階段用白名單判斷。is_streamable 只接受 Column、Literal、Binary、Ternary、Cast 和 elementwise 函式；任何 over()、shift、cum_*、rank 都會讓整個節點出局（aexpr/utils.rs#L10-L65）逐節點、逐表達式 lower，做不到的才包進 InMemoryMap，而且只預先選需要的欄位（lower_expr.rs#L406-L485）
運算子覆蓋get_operator 只有 projection、select、with_columns、filter、map、union，其他一律 panic（convert.rs#L574-L643）。Join 只支援 cross/left/full/coalesced inner，semi、anti、asof 都退回（checks.rs#L27-L43）50+ 種 PhysNodeKind：equi、merge、semi/anti、cross、asof、range join，sorted/dynamic/rolling group-by，top-k，window，各格式的 source 與 sink（physical_plan/mod.rs#L173）
Group-by 聚合每個表達式只能是單一個 sum/first/last/mean/count/len，或不傳播 NaN 的數值 min/max；median、std、quantile、n_unique 都不行（aggregates/convert.rs#L50-L120）新的 group-by 實作（#22285）採 hash 分區，每個分區帶基數 sketch（group_by.rs#L61-L113）
Spill to disk只有 sort 和 generic group-by 會 spill。最常見的整數 key、字串 key group-by 寫死 ooc=false，註解是「this ooc is broken fix later」（primitive/mod.rs#L95-L105）。它的 OocState 開頭寫著「THIS CODE DOESN'T MAKE SENSE」（ooc_state.rs）。Join build side 全部留在 RAM統一的 polars-ooc：morsel 本身就是 SpillFrame，sort、group-by 冷資料、join build side、multiplexer 與最終結果都註冊到 spill context（見 6.3）
順序每個 source 從一個行程全域的 static CHUNK_INDEX: AtomicU32 拿編號，最後由 OrderedSink 收齊再 sort_unstable_by_key（sources/mod.rs#L24-L28、ordered.rs#L26-L59）。需要順序保證的運算一律拒絕MorselSeq 是結構的一部分，linearizer 做串流式 k 路合併；需要順序時照樣能跑，只是付平行度的代價
排程rayon scope 鎖步，每執行緒一份 operator 副本，stage 之間沒有流量控制自製 async 執行器、兩級優先、work stealing、背壓
和 optimizer 的關係streaming=True 時直接關掉 CSE（frame/mod.rs#L611-L614）共用子計畫變成 Multiplexer 節點，落後的消費者用可 spill 的緩衝（physical_plan/mod.rs#L871-L902）

那新引擎在 1.0 時是什麼狀態？polars-stream 已經存在，但只有約 3,400 行，lib.rs 頂端還掛著 #![allow(unused)] // TODO: remove。PhysNode 只有 InMemorySource、Select、Filter、SimpleProjection、InMemorySink、InMemoryMap、Map、Sort 這幾種，lower_ir 遇到其他節點就 todo!()（1.0 lower_ir.rs#L72-L150）。Python wheel 甚至沒有把它編進去，"new_streaming" 在 feature 清單裡是註解掉的（py-polars/Cargo.toml#L231-L244）。

不過骨架上的關鍵決定在 1.0 前就已經做了：自製 async 執行器、Morsel 帶 MorselSeq、port 狀態圖。第一個 commit 是 2024-06-12 的 #16884（"add fundamentals for new async-based streaming execution engine"）。1.0 的發布文章也已經描述這個方向：結合 morsel-driven parallelism 與 Rust 的 async state machine，做成 push/pull 混合的引擎，rolling window 這類需要更多同步的運算則退回 in-memory。

移除舊引擎的 PR（#23103，Orson Peters）說得很直接：「The old streaming engine was experimental, and deprecated for a while now」，而且它「started breaking more and more and becoming a maintenance issue」。這個 PR 刪掉約 1.2 萬行。

06難關與技術選擇

6.1 行順序：最難的是語意，不是程式

DataFrame 使用者習慣「資料怎麼進來就怎麼出去」。in-memory 引擎多半順手做到了，例如 left join 保持左表順序，於是很多程式碼不知不覺依賴這件事。streaming 引擎想要全速平行，就得允許 morsel 亂序完成。舊引擎的做法是拒絕所有需要順序的運算；新引擎的選擇分成三層：

  • 引擎層：序號是 morsel 的一部分，需要時用 linearizer 合併，代價是失去部分平行度。
  • 語意層：2.0 把「順便的順序」從合約中拿掉，需要時明確寫 maintain_order 或 sort。join 的 maintain_order 預設 None，文件說它「might differ across Polars versions or even between different runs」（frame.py#L6066-L6081）。
  • Optimizer 層：simplify_ordering 從計畫中找出順序真正被觀察的地方，其餘的邊標成 Unordered。
// simplify_ordering：join 沒要求順序 → 兩個輸入和輸出都標成無序
if out_edge.is_unordered() || options.args.maintain_order == JO::None {
    *out_edge = Edge::Unordered;
    *in_edge_lhs = Edge::Unordered;
    *in_edge_rhs = Edge::Unordered;
    Arc::make_mut(options).args.maintain_order = JO::None;
}

這段程式碼把代價寫得很清楚：要保持順序，join 就不能按 partition 批次 probe，只能跟著 probe morsel 的順序走。這就是為什麼「預設不保證順序」是讓 streaming 成為預設的前提。值得注意的是，順序可觀察性的 optimizer pass 本身比 2.0 早很多（#20396，2024-12；2026-04 改寫成 simplify_ordering，#27075）。2.0 改變的是預設引擎開始真正吃下這份自由，配套 PR 有 #27883（為非有序 join 改寫測試）。

6.2 覆蓋率：每個運算子都要重寫一次

streaming 版的運算子和 in-memory 版是不同的演算法。group-by 要 hash 分區加冷熱分離，equi-join 是 Sample → Build → Probe → EmitUnmatched → Done 的狀態機（equi_join.rs#L1427-L1434），sort 要取樣、分桶、可 spill。兩個 tag 之間有 885 個 commit 碰過 polars-stream，光 lowering 的程式就有 lower_ir.rs 2,148 行、lower_expr.rs 3,287 行、lower_group_by.rs 1,455 行。

技術上的選擇是逐節點 fallback：做不到的部分用 InMemoryMap 或 InMemoryJoin 包起來，讓整個查詢仍然能用 streaming 跑。例如 unique(maintain_order=True, keep="last") 到 2.0 仍走這條路（lower_ir.rs#L1722-L1765）。代價是 fallback 節點要把輸入整份收齊，命中 fallback 的查詢就拿不到記憶體優勢。舊引擎則是整棵子樹二選一，所以一個不支援的表達式就足以讓上半部全部物化。

6.3 Pipeline breaker 與 out-of-core

串流解決不了需要看到全部資料的運算：sort、group-by 的狀態、join 的 build side。2.0 的答案是新 crate polars-ooc，它有三個部分：

  • 精確計帳。包住 jemalloc/mimalloc 的 GlobalAlloc，每次 alloc/dealloc 先記在 thread-local 的漂移計數器，超過 4 MiB 才合併進全域 atomic（global_alloc.rs#L28-L52）。Python wheel 把它設成 #[global_allocator]（#27103）。
  • 何時 spill。每次運算子註冊一塊緩衝資料，就檢查「用量＋預取中 − spill 中」是否超過預算；預算是 0.8 × 總 RAM（會看 cgroup）與 POLARS_OOC_MEMORY_BUDGET_MB 取小（memory_manager.rs#L61-L67）。選誰 spill 用 Thompson sampling 挑 spill context，分 MostRecent、LeastRecent、Random 三種淘汰策略。
  • 怎麼 spill。寫成 Arrow IPC stream，可選 zstd，存到 /var/tmp/polars-$USER/spill；SpillToken 有 pin 計數，get().await 時透明地讀回來（spill_frame.rs#L19-L85）。
// sort：每個緩衝的 morsel 都註冊到 LeastRecentSpillContext
bytes.fetch_add(df.estimated_size(false) as u64, Ordering::Relaxed);
let keys = key_series(&df, key)?;
sample.add(&keys);
...
spill_ctx.register(morsel.sf()).await;

sort/mod.rs#L406-L416 · 超過 min(32 MiB, budget/2) 改走範圍分桶，見 #L135-L161 · group-by 冷資料 group_by.rs#L437 · join build equi_join.rs#L745

還沒完成的部分：hash table 和 group-by 的 hot table 本身不能 spill，只有緩衝的 frame 可以；sort 的 partition builder 註解明說「can't be spilled」（tuning.rs#L9-L12）。repo 裡唯一的 OOC Python 測試還標著 @pytest.mark.skip，相關設定也全在 // Private. 區塊，沒有文件。官方 2.0 文章把這稱為「initial out-of-core support」。這塊應該視為剛起步。

6.4 排程：為什麼自己寫 async 執行器

rayon 的 fork-join 模型適合「一個運算子內部平行」，正好是 in-memory 引擎的需求。但 streaming 需要很多長壽、會互相等待的任務：source 等下游消化、linearizer 等某條 pipeline、join 的 probe 等 build 完成。這種情況用 async state machine 表達最自然：等待時讓出執行緒，不必阻塞。Polars 因此寫了自己的執行器，加上優先級（先消化再生產）與 NUMA 感知的 work stealing。推論 這也是舊引擎鎖步問題的根本解法：沒有全域 barrier，慢的 morsel 只拖住自己那條 pipeline。

6.5 Optimizer 跟著長大

optimizer 目錄從 8,308 行長到 21,351 行。對照兩版 optimize() 的 pass 順序（橘色是 2.0 新增或位置有改變的）：

1.0 · optimizer/mod.rs#L60-L235

  1. to_alp（內含 type coercion、simplify）
  2. CSPE 共用子計畫消除
  3. Projection pushdown（在 predicate 前）
  4. Predicate pushdown
  5. cluster_with_columns
  6. 規則迴圈：SimpleProjectionAndCollapse、DelayRechunk、SlicePushDown、SimplifyBoolean、FlattenUnion
  7. set_cache_states
  8. CSE（表達式）

2.0 · optimizer/mod.rs#L104-L382

  1. CSPE 共用子計畫消除
  2. Slice pushdown → Predicate pushdown（含 cross join + filter 折成 equi/IE join）
  3. CollapseSort
  4. outer join pushthrough、join_order、join predicate fusion
  5. Projection pushdown（移到 predicate 之後，#26688）
  6. 規則迴圈：FusedArithmetic、SimpleProjectionAndCollapse、DelayRechunk、FilterConstraintRule、SimplifyBoolean、FlattenMergeSorted、FlattenUnion
  7. 第二次 slice pushdown、join build side、join runtime filters
  8. cluster_with_columns、CSE、extract_windows
  9. simplify_ordering（CHECK_ORDER_OBSERVE）
  10. expand_datasets、DSL resolvers、prune parquet metadata

從 CMU optimizer 課的角度，最有意思的是 2.0 第一次出現 cost-based 的成分。1.0 是純 rule-based，唯一的估計 row_estimate 只用來讓舊 streaming 引擎選 join build side。2.0 則有：

  • 基數模型（#29024）：join 大小用教科書公式 |A|·|B| / Π domain(key)，domain 取兩側 NDV 的最大值，沒有 NDV 時用整數 min/max 範圍（stats/node.rs#L781-L785）；預設選擇率 0.2；估計值帶 Card::{Unknown, Exact, Approx{rel_err}} 信心標籤。
  • Join reordering（#28985，2026-08-26）：找出連續的 inner equi-join，用貪婪 left-deep 搜尋。每個葉子都試一次當起點（上限 24 個葉子），不引入原本沒有的 cross product，成本是中間結果大小總和（join_order/enumerate.rs#L11-L91）。模組文件寫得很實際：「The estimates can be wrong, so it skips any cluster it cannot measure」（join_order/mod.rs#L1-L14）。
  • Join runtime filter：hash join build 完成後，把 min/max 範圍與 bloom filter 推到 probe 側的 parquet scan（join_runtime_filter.rs#L1-L30）。這個技巧在 streaming 下特別划算，因為 probe 側還沒開始讀。

推論 這仍然不是 System R 或 Cascades 式的 optimizer：沒有對 join 子集合做 DP，沒有 physical property 列舉，也沒有全計畫的成本搜尋。它是固定的規則管線，裡面嵌一個用估計值的 join ordering pass。統計來自 parquet footer、Iceberg manifest 與取樣，不是 ANALYZE 產生的直方圖。對照課程內容，這是 rule-based 系統逐步加入 cost model 的典型路線。

Predicate pushdown 經過 join 的邏輯也變聰明了。2.0 會用 join key 等值關係把 key 上的 filter 同時推到兩側（transitive predicate transfer），也會在 filter 會剔除 null 列時把 Full 降成 Left/Right、把 Left/Right 降成 Inner，也就是經典的 outer join simplification（predicate_pruning.rs#L402-L424）。1.0 的版本在 predicate_pushdown/join.rs#L123-L257，可以對照著讀。

07為什麼是現在：決策因素

原始碼不會說「我們為什麼選這個時間點」。下面六點把可以驗證的事實和我的推論分開標示。

A

覆蓋率過了門檻。native 節點涵蓋所有 join 類型、各種 group-by、sort/top-k、window 和全部 IO 格式，fallback 從「常態」變成「例外」。#27822 本身也動到了 lower_group_by.rs 與 lower_ir.rs。

事實 節點清單見 PhysNodeKind　推論 門檻是團隊主觀判斷的

B

效能證據夠強。官方 PDS-H 顯示 streaming 快 3～7 倍，資料越大差越多，這讓「預設慢一點換省記憶體」的顧慮不存在。

事實 官方自測數字　推論 這是說服使用者接受 breaking change 的主要論據

C

行順序必須等 major 版本。預設引擎換掉會悄悄改變結果順序，semver 下只能放進 2.0。官方文章也明說升 major 是為了這個。

事實 upgrade/2.md 的 danger 框

D

記憶體安全網要在預設之前就位。streaming 變成預設後，pipeline breaker 的狀態若沒有 spill 機制，大查詢一樣會 OOM。OOC 在發布前一天才預設開啟。

事實 #29741（2026-10-05）　推論 時間點顯示它是趕在 2.0 前補上的

E

維護兩顆引擎太貴。舊引擎因「maintenance issue」被刪除。2.0 的 in-memory 引擎連檔案 scan 都已委派給 streaming 的子執行器，兩顆引擎在收斂。CI 也移除了 auto-streaming job，streaming 成為主要測試路徑（#29214）。

事實 mem-engine planner/lp.rs#L467-L524　事實 #23103 說明文字

F

產品方向。開啟 query monitoring 時，Python 會把 engine affinity 設成 "streaming"；per-node 執行指標也只有 streaming 引擎能回報到 Polars Cloud。

事實 config.py#L1689　推論 雲端與分散式執行需要 morsel 這種可切分、可觀測的單位

回到你的三個問題，濃縮成一句：以前不做，是因為舊引擎的設計（白名單、鎖步、全域計數器、半套 OOC）撐不起預設，新引擎在 1.0 時還只是骨架；後來做，是因為覆蓋率、效能證據和 OOC 都到位，而且碰上可以改語意的 major 版本；中間的難關是順序語意、每個運算子的重寫，以及 pipeline breaker 的記憶體上限。
